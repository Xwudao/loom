# Loom 设计说明

> Compile-time dependency injection for modern Go.
> 本文档记录 Loom 的关键设计决策，以及这些决策背后的 Go 语言约束。

## 0. 调查结论（Phase 0）

调研范围：`google/wire`、`goforj/wire`、`uber-go/fx`、`uber-go/dig`、
`shanjunmei/dig`、`samber/do`，以及 `go/types` / `go/packages` 的现状。

关键发现：

| 项目 | 模式 | 结论 |
| --- | --- | --- |
| `google/wire` | codegen + injector stub（build tag） | **已停止维护**（README 明说 no longer maintained）。无泛型支持，cleanup 是裸 `func()`，接口绑定需要额外 `wire.Bind`。 |
| `goforj/wire` | wire fork | 沿用 wire 的 injector stub 模型，仍无泛型。 |
| `uber-go/dig` | runtime reflection container | 运行时反射/容器，与 Loom 目标相反，仅借鉴错误信息与 graph 可视化。 |
| `uber-go/fx` | dig + lifecycle | lifecycle 的 hook 顺序 / rollback 语义值得借鉴，但整体是 runtime container。 |
| `samber/do` | runtime generics container | 用泛型改善 API，但仍是运行时容器 + 反射。 |

**Go 现状（实测于 go1.27）**

- 泛型函数/类型实例化信息可完整获取：
  `types.Info.TypeOf(expr)` 对 `NewRepository[User]` 直接返回**实例化后的** `*types.Signature`；
  `types.Info.Instances` 可拿到 `TypeArgs`。
- `types.Identical` / `types.AssignableTo` / `types.Implements` 可正确区分
  `*Repository[User]` 与 `*Repository[Article]`。
- `partial type argument lists`（Go 1.21+）使 `loom.As[UserStore](NewUserStore)`
  这种「只给接口类型参数、函数类型参数自动推断」的写法可以成立（AST 为 `IndexExpr`）。
- `golang.org/x/tools/go/types/typeutil.Map` 提供以 `types.Identical` 为相等语义、
  以结构化 hash 为索引的 type→value map，正好是 TypeKey 需要的语义。
- `go/packages` 默认遵循 `//go:build` 约束，无需自行解析 build tags。

因此 Loom 的核心选择是：**用 `go/types` 做类型身份判定，用 `go/packages` 做构建约束，
生成普通 Go 代码，运行时只保留一个极小的 lifecycle 原语。**

## 1. Marker API 最终选择

### 1.1 被否决的方案

**方案 A：Wire 风格 injector + build tag**

```go
//go:build loomgen
func InitApp() (*App, error) { loom.Build(...); return nil, nil }
```

缺点：injector 文件在正常构建中被 build tag 排除，**gopls 默认看不到图声明**，
编辑体验差；需要维护两套 build tag；clean-checkout 依赖 stub 的假返回值。

**方案 B：`func InitApp() *App { return loom.Build[*App](...) }` + generator 重写函数体**

缺点：需要**改写用户源文件**（破坏 DO NOT EDIT 约定、git diff 噪声、格式化/注释丢失风险）；
或者需要 build tag 排除用户文件（回到方案 A 的问题）。

**方案 C：`var InitApp = loom.Graph[...]().Func()` + init() 覆盖**

缺点：依赖包级 `init()` 顺序，运行时仍有间接跳转，且同包内其它包级变量初始化会看到 stub。

### 1.2 采用方案：声明式 Graph 变量 + 生成独立函数

```go
// user code —— 普通文件，始终参与构建
var AppGraph = loom.Graph[*Application](
    loom.Provide(NewConfig),
    loom.Provide(NewDB),
    loom.Provide(NewRepository[User]),
    loom.As[UserStore](NewUserStore),
    loom.Provide(NewApplication),
)
```

```go
// loom_gen.go —— generator 生成
// Code generated by loom. DO NOT EDIT.

func InitApp() (*Application, *loom.Lifecycle, error) { ... }
```

理由：

1. **图声明在普通文件里**，`gopls`、`go vet`、`go test` 都能完整看到并类型检查，
   可以直接跳转/重命名 provider 引用。这是相对 Wire 的核心体验改进。
2. `loom.Graph[T]` 用类型参数 `T` 固定目标类型，图的目标类型是**编译期强制**的。
3. 不需要 build tag，不需要改写用户文件，生成物是独立文件，符合 `DO NOT EDIT` 约定。
4. 生成函数名由变量名确定推导，可用 `loom.Name("...")` 覆盖，**完全确定**。

### 1.3 生成函数命名

| 声明 | 生成函数 |
| --- | --- |
| `var AppGraph = loom.Graph[*App](...)` | `InitApp` |
| `var appGraph = loom.Graph[*App](...)` | `InitApp` |
| `var Worker = loom.Graph[*Worker](...)` | `InitWorker` |
| `var AppGraph = loom.Graph[*App](loom.Name("BuildApp"), ...)` | `BuildApp` |

规则：去掉变量名的 `Graph`/`graph` 后缀，首字母大写，加 `Init` 前缀。
若变量名恰好就是 `graph`，保留后缀得到 `InitGraph`（不强制 `loom.Name`）。
同一包内名字冲突 → 编译期错误。

### 1.5 类型名与函数名的冲突

Go 的包级标识符共享一个名字空间，因此 `func Module(...)` 与 `type Module`
不能共存。最终导出类型名：

```go
type Option interface{ loomOption() }   // sealed
type Provider struct{ marker }          // loom.Provide / As / Supply 的返回类型
type ModuleDef struct{ marker }         // loom.Module 的返回类型
type GraphDef[T any] struct{ marker }   // loom.Graph 的返回类型
```

marker 类型都嵌入了未导出的 `marker`，所以外部无法实现/构造非法标记，
但它们本身是零大小值，除了包初始化时少数几次空赋值外没有运行时代价。

### 1.4 生成函数签名（固定，不随 provider 变化）

```go
func InitApp() (*Application, *loom.Lifecycle, error)
// 或加上 loom.WithContext() 选项：
func InitApp(ctx context.Context) (*Application, *loom.Lifecycle, error)
```

- **固定签名**：不根据「有没有 lifecycle hook」推断签名，避免新增 provider 时调用点“无故”变化。
- 始终返回 `*loom.Lifecycle`：它是运行时唯一的原语，承担 Start/Stop/rollback。
- `loom.WithContext()` 是显式选项：声明后，`context.Context` 成为可注入依赖，
  rollback 也复用同一个 ctx。没有该选项时注入 `context.Context` 会得到带提示的错误。
- `loom.Supply` 用于把既有值送进图（详见 §5）。

## 2. Provider 模型

合法 constructor 形状（`v1` 第一版严格限定为**单一输出值**）：

```
func(...) T
func(...) (T, error)
func(...) (T, Cleanup)
func(...) (T, Cleanup, error)
```

其中 `Cleanup = func(context.Context) error`；也接受 `func()` / `func(context.Context)`
（generator 生成适配闭包）。

不支持多输出 provider（`func() (A, B)`）。理由：部分构造语义、重复检测、
rollback 都会复杂化；用户可以拆成两个 provider。IR 不为多输出预留结构，
但 `Output` 是独立字段，将来扩展成本低。

provider 必须是**包级函数、包级 var/const（函数类型）、泛型函数的实例化形式**。
拒绝方法值、函数字面量、闭包，给出明确错误（生成代码需要稳定的可引用符号）。

## 3. Cleanup 与 Lifecycle 语义

这是 v0.1 最容易含糊的地方，规则如下（**唯一来源**）：

1. `Cleanup` 由 constructor 返回，表示「构造期获得的资源」。
2. 构造过程中，每个 cleanup **在对应 provider 成功返回后立即**注册进 lifecycle
   （`lifecycle.AddCleanup`），保持构造顺序。
3. 构造失败（某个 provider 返回 error）：调用 `lifecycle.Rollback(ctx)`，
   按**注册逆序**执行所有 cleanup，错误与原错误 `errors.Join` 后返回。
4. 构造成功：用户对返回的 lifecycle 调用 `Start(ctx)` / `Stop(ctx)`。
   `Stop` 按**注册逆序**执行：已 start 的 hook 的 `OnStop`，以及全部 cleanup。
5. 因此 **cleanup 与 hook 在同一条有序链上**，Stop 的逆序天然保证
   「依赖者先于被依赖者释放」。
6. `Rollback` 只执行 cleanup，不执行从未 Start 过的 hook。
7. 禁止：同一资源既返回 cleanup、又注册 `OnStop` hook（会导致重复释放）。
   文档明确 + 测试覆盖单一风格。

为什么 `Cleanup` 带 `context.Context`：与 hook 统一签名，`Stop(shutdownCtx)`
的超时预算可以传导到资源释放；构造失败 rollback 使用 builder 的 ctx
（无 `WithContext` 时为 `context.Background()`）。

### Lifecycle 状态机

```
                       ┌───────────────┐
        Start ────────▶│   starting    │──── 全部成功 ──▶ started
                       └───────┬───────┘
                               │ 某个 hook 失败
                               ▼
                        stop 已注册链（逆序）
                               │
                               ▼
                            failed ── Start▶ ErrStartFailed
                                     ── Stop ▶ nil
        Stop ─────────▶ stopping ──▶ stopped ── Stop▶ nil（幂等）
```

- `Start`：注册顺序执行 `OnStart`；`ctx` 取消或 hook 失败 → 逆序回滚已 start 的 hook + cleanup，
  返回 `errors.Join(startErr, rollbackErrs...)`；之后状态为 `failed`，不可重启。
- `Stop`：逆序执行；`ctx` 取消则记录错误并**停止继续**（把超时控制权交给调用者）；
  所有 hook 错误用 `errors.Join` 聚合；重复 `Stop` 返回 nil。
- hook panic 被 recover 并转成 error，参与 rollback/聚合；不吞掉其它 hook。
- `Append` / `AddCleanup` 只允许在 Start 之前（含 starting 阶段），之后调用 panic，
  避免「启动后再偷偷注册 hook」这种不可推理的行为。
- 并发：内部 `sync.Mutex`；`Start`/`Stop` 由状态机拒绝重入。

## 4. 泛型与 TypeKey

- 每个 provider 的输入/输出都是 `go/types.Type`，**不构造字符串类型键**。
- 依赖索引使用 `typeutil.Map`（hash 索引 + `types.Identical` 相等判定），
  因此 `*Repository[User]` 与 `*Repository[Article]` 是两个 key。
- 泛型 provider 必须**已实例化**：`loom.Provide(NewRepository[User])`。
  未实例化的泛型函数作为值本身就无法通过 Go 类型检查（编译器先报错），
  若通过包级 var 间接传入则 generator 报错并提示实例化写法。
- 别名（含 Go 1.24+ generic alias）统一走 `types.Unalias`，身份仍由 `types.Identical` 决定。

## 5. Supply

`loom.Supply(expr)` 的值必须能被**搬进生成代码**。因此约束：

- 只接受不需要运行时容器、可在生成文件中原样重现的表达式：
  包级标识符、`pkg.Name`、字段选择链、基础字面量、复合字面量、函数调用
  （函数与被调参数同样受限）。
- 禁止引用局部变量（图声明必须在包级，天然满足）。
- 生成代码在 `Init*` 中求值一次，**不进入任何运行时容器**。
- 由于 Go 会在包初始化时求值 `Supply` 的参数，若参数含副作用调用会被执行两次；
  因此 generator 拒绝含函数调用的 `Supply` 参数？——不，允许调用，但文档说明：
  值在包初始化与 `Init*` 中各求值一次，若需要单次求值请先赋给包级变量。
  （测试覆盖 `Supply(pkgVar)` 与 `Supply(composite literal)`。）

> 实现取舍：v0.1 支持「表达式原样重现」，副作用语义写进文档与测试，不做运行时缓存。

## 6. 解析与诊断

统一 `Diagnostic{Message, Position, Path}`，Path 是 `root -> ... -> missing` 的依赖链。
错误文案面向人：

```
loom: missing provider for UserStore

dependency path:
    *Application
      -> *HTTPServer
      -> *UserService
      -> UserStore  (missing)

required by:
    NewUserService  internal/user/service.go:18
```

cycle、duplicate 同理，均带路径与源码位置。

## 7. 代码生成

- 通过 `go/packages` 加载（`NeedTypes|NeedTypesInfo|NeedSyntax|NeedDeps|NeedImports`），
  build tags 交给 go 工具链。
- 输出 `loom_gen.go`；先构造 import 管理表与变量名分配表，再文本生成，最后 `go/format`。
- 变量名从类型推导：`*Config → config`、`Repository[User] → userRepository`，
  冲突加数字后缀；保留字与 import 别名预占。
- import alias 冲突用数字后缀，排序确定。
- 生成结果与已有文件**字节相同则不写盘**（保护 mtime / IDE / git）。
- 同一输入必须字节级确定。

## 8. 为什么没有 runtime container

生成后的 `InitApp` 是普通 Go 代码：直接调用 constructor、直接传参。
运行时依赖只有 `loom.Lifecycle`（hook/cleanup 的有序列表）。
没有 `Container`、`Resolve`、`Get`、反射、`map[reflect.Type]`。
依赖解析、类型匹配、环检测、缺失检测全部发生在 `loom generate`。

## 9. v0.1 不做

named/keyed dependency、optional、group、decorator、scope（transient/request）、
runtime replace、plugin。IR 保留 `Output`/`Binding` 独立字段，不堵死未来扩展。
